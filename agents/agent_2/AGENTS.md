## Mission

Для каждого объекта наблюдения из каталога (`agent_1_v5.
observation_objects`) отобрать из корпуса новостей (`agent_1_v5.
clean_posts`) конечный набор документов — решение «берём / не берём»,
не ранжированный список.

Конструкция (не переоткрывать без нового замера —
`docs/architecture/retrieval_research_report.md`):

1. Лексический канал — regex ключевых слов объекта по заголовку и тексту.
2. Векторный канал — эмбеддинг `search_description` объекта, top-500 по
   HNSW.
3. Объединение (union, не пересечение) кандидатов обоих каналов.
4. LLM-оценка каждого кандидата 0–10 по словесной рубрике, через
   OpenClaw (не напрямую в провайдера).
5. Порог 7.5.
6. Негатив-фильтр каталога как вето — после порога, не вместо него.
7. Запись прошедших в `agent_1_v5.agent_2_relevant_documents`.

Каталог объектов агент получает готовым — он не порождает объекты и не
переписывает присланные поля. KR, драйверы и «Упоминания» — не его
забота: это работа другого, будущего агента, который читает
`agent_2_relevant_documents` как вход.

## Hard Boundaries

Из брифа (`docs/architecture/ONBOARDING_filter_agent.md`, разделы 7–8):

- Не трогать `agent_1.processing_jobs` — боевая очередь Агента 1.
- Не запускать `parsers360_ingest` без явного указания — поход в сеть.
- Секреты и приватные данные не коммитить (ключи — в `.env`, вне Git).
- `trash` вместо `rm`.
- Не грузить CPU: тяжёлые модели (кросс-энкодеры и т.п.) — через API,
  не локально.
- Всё внешнее и необратимое — подтверждать у Капитана.
- Не оперировать понятиями KR, драйвер, упоминание — вне контракта
  этого агента (`specs/agent_2/spec.md`, требование «KR и драйверы —
  вне ответственности агента 2»).

## Output Style

- Называй объект наблюдения (id + label), с которым работаешь.
- Число кандидатов, число прошедших порог, число отсеянных вето —
  явно, не скрыто в логах.
- Разделяй то, что подтверждено эталоном (`labels_v2.jsonl`), от того,
  что не проверено — см. брифу раздел 9 «чего в замерах нет».
