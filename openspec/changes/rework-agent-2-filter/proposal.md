## Why

Пайплайн v5 (`docs/architecture/pipeline_v5_context.md`) описывал Агента 2
как генератор объектов из бизнес-цели (КР → темы, ключевые слова, веса
источников). Концепция объектов наблюдения (`docs/architecture/
observation_objects_context.md`) эту работу забирает: каталог объектов
(название, алиасы, ключевые слова, негатив-фильтр, веса источников)
приходит уже готовым от внутреннего агента банка. Генерация внутри
контура больше не нужна, а вот отбор документов под уже готовый объект —
нужен, и его никто не делает.

Исследование ретрива (`docs/architecture/retrieval_research_report.md`,
1318 размеченных документов) закрыло вопрос конструкции: запрос по
описанию объекта, объединение лексического и векторного каналов, граница
по оценке LLM с порогом 7.5. Рабочий прототип есть
(`experiments/retrieval_eval/filter_agent.py`), но он не встроен в
пайплайн, не подключён к каталогу боевых объектов и режет по устаревшей
отсечке (разрыв в распределении, не LLM-рубрика — см. шапку файла).

## What Changes

- Старый `agents/agent_2/` (промпт-агент «бизнес-цель → JSON с темами/
  ключевыми словами/весами источников») архивируется. Код и промпты не
  удаляются, но выходят из состава пайплайна.
- На месте агента 2, под тем же номером, встаёт агент-фильтратор: по
  каталогу объектов наблюдения и корпусу новостей отбирает для каждого
  объекта конечный набор документов (решение «берём / не берём», не
  ранжированный список).
- Поле `search_description` добавляется в контракт объекта наблюдения
  (`docs/architecture/proposal_search_description.md`) — источник текста
  для эмбеддинга запроса; без него объекты-понятия (доверие к ИИ,
  регуляторика, инциденты) не находятся векторным каналом.
- Прототип `filter_agent.py` переносится в постоянный код агента, отсечка
  по разрыву в распределении заменяется на LLM-оценку по рубрике 0–10 с
  порогом 7.5 (уже задокументированное в прототипе, но не реализованное
  решение).
- Вызов решающей LLM идёт через OpenClaw (тот же паттерн, что у
  `agent_1/label_kr_worker.py`: `--openclaw-cmd`/`--agent-id`/`--model`),
  а не напрямую в OpenRouter API, как в прототипе. Модель (Opus/Sonnet)
  не хардкодится — решается конфигурацией вызова.
- **BREAKING**: контракт входа расширяется обязательным полем
  `search_description`; агент 2 меняет назначение (было: генерация
  объектов из КР; стало: фильтрация документов под готовый объект) —
  любой код, ожидающий старый выход агента 2, ломается.

## Capabilities

### New Capabilities
- `agent_2`: место агента 2 в пайплайне v5 — вход (каталог объектов
  наблюдения), выход (`agent_1_v5.agent_2_relevant_documents` — отобранные
  документы по объекту, без понятия драйвера/упоминания), правила
  репозитория, границы с соседними агентами (архивированный старый
  агент 2, будущий агент-экстрактор драйверов — вне скоупа, читает выход
  агента 2 как вход).
- `agent_2-filtering`: сама механика отбора — лексический канал (regex
  каталога), векторный канал (эмбеддинг `search_description`, top-500),
  объединение каналов, LLM-оценка по рубрике с кэшем и порогом 7.5,
  негатив-фильтр как вето, регрессионный тест на эталоне (полнота ≥70%).

### Modified Capabilities
(нет — `agent_2` в `openspec/specs/` ранее не существовал; это первая
спека для этого агента, не правка существующей)

## Impact

- Код: новый пакет для агента-фильтратора (по аналогии с
  `agents/agent_1/src/agent_1/`); `experiments/retrieval_eval/
  filter_agent.py`, `patterns.py`, `queries.py` переиспользуются как
  основа, не переписываются с нуля. Старый `agents/agent_2/*` (промпт,
  AGENTS.md, SOUL.md и т.д.) архивируется на месте, не удаляется.
- БД: три новые таблицы в схеме `agent_1_v5` (решение 2026-08-06, см.
  `design.md`, D10) — `observation_objects` (каталог), `agent_2_llm_scores`
  (кэш решающей оценки), `agent_2_relevant_documents` (итог отбора,
  M:N объект↔документ). Драйверы и «Упоминания» — не в этой схеме и не
  в скоупе агента 2. КР (Key Results) агент 2 не касается вовсе.
- Контракт объекта наблюдения: добавляется `search_description`
  (обязательное поле) — затрагивает то, что банк обязан присылать, и то,
  что примет агент 2 на входе.
- Внешние зависимости: OpenClaw CLI для вызова решающей LLM (вместо
  прямого OpenRouter), эмбеддинг-модель без изменений
  (`text-embedding-3-small`, dims=1024 — пересчёт корпуса асимметричной
  моделью отложен отдельным решением).
- Эталон `experiments/retrieval_eval/data/labels_v2.jsonl` (1318
  документов) становится частью регрессионного теста агента, не только
  экспериментальным артефактом.
- Правила репозитория, действующие на реализацию: не трогать
  `agent_1.processing_jobs`, не запускать `parsers360_ingest` без явного
  указания, `hnsw.ef_search` только через `set_config()`, 429 от LLM —
  не фатальная ошибка (нужен пейсер/Retry-After), кэш решающей оценки
  обязан включать модель в ключ.
