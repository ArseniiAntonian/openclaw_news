## ADDED Requirements

### Requirement: Лексический канал по ключевым словам каталога
Фильтратор MUST искать документы по regex ключевых слов, заданных
объектом в каталоге (`patterns.py`/`to_postgres()` или их прямой аналог),
по заголовку и очищенному тексту документа. Канал MUST выполняться
независимо от векторного канала.

#### Scenario: Документ содержит ключевое слово объекта
- **WHEN** заголовок или текст документа matches regex ключевых слов
  объекта
- **THEN** документ попадает в результат лексического канала

### Requirement: Векторный канал по поисковому описанию объекта
Фильтратор MUST выполнять семантический поиск по эмбеддингу
`search_description` объекта, а не по названию объекта и не по алиасам.
Глубина выдачи MUST быть не меньше 500 документов на объект.
`hnsw.ef_search` MUST устанавливаться не меньше глубины выдачи через
`set_config()`, а не через `SET ... = %s` с параметром (последнее
синтаксически не работает — `SET` принимает только литералы).

#### Scenario: Запрос строится из поискового описания
- **WHEN** фильтратор формирует запрос векторного канала для объекта
- **THEN** текстом запроса служит `search_description` объекта, эмбеддится
  он, а не название/алиасы

#### Scenario: Глубина поиска
- **WHEN** векторный канал выполняет поиск по объекту
- **THEN** возвращается не менее 500 документов, отсортированных по
  убыванию близости

### Requirement: Каналы объединяются, а не пересекаются
Итоговый набор кандидатов до порога MUST быть объединением (union)
множеств лексического и векторного каналов. Реализация, применяющая
ключевые слова как фильтр после векторного поиска (пересечение), MUST
быть отклонена: замер показал проигрыш пересечения ключевым словам на
восьми объектах из восьми.

#### Scenario: Документ найден только одним каналом
- **WHEN** документ попал в выдачу векторного канала, но не совпал ни с
  одним ключевым словом (или наоборот)
- **THEN** документ всё равно входит в объединённый набор кандидатов

### Requirement: Решающая оценка — LLM по словесной рубрике, порог 7.5
Каждый кандидат из объединённого набора MUST получать оценку 0–10 от LLM
по словесной рубрике (десять — новость целиком об объекте, четыре-шесть —
объект упомянут, но новость про другое, ноль — не относится). Документ
MUST включаться в итоговый набор, если оценка ≥7.5. Отсечка по разрыву в
распределении оценок/косинуса (адаптивный порог на основе позиции обрыва)
MUST NOT использоваться как решающее правило: единого порога у неё нет,
она эквивалентна фиксированному K.

#### Scenario: Оценка выше порога
- **WHEN** LLM оценивает кандидата на 7.5 или выше
- **THEN** документ входит в итоговый набор (до применения негатив-фильтра)

#### Scenario: Оценка ниже порога
- **WHEN** LLM оценивает кандидата ниже 7.5
- **THEN** документ не входит в итоговый набор

### Requirement: Вызов решающей LLM — через OpenClaw
Батчевые вызовы решающей LLM-оценки MUST выполняться через OpenClaw
(паттерн `--openclaw-cmd`/`--agent-id`/`--model`, аналогично
`agent_1/label_kr_worker.py`), а не напрямую в OpenRouter или другой
провайдерский API. Конкретная модель (например, Opus или Sonnet) MUST
быть параметром конфигурации вызова, а не значением, зашитым в код агента.

#### Scenario: Оценка кандидата
- **WHEN** фильтратор запрашивает решающую оценку для кандидата
- **THEN** запрос уходит через OpenClaw-обвязку, модель берётся из
  конфигурации вызова

### Requirement: Кэш решающей оценки учитывает модель
Кэш решающих оценок MUST храниться в таблице
`agent_1_v5.agent_2_llm_scores` с первичным ключом (`id_object`,
`id_clean_post`, `model`). Оценка, полученная одной моделью, MUST NOT
молча переиспользоваться при запросе с другой моделью.

#### Scenario: Смена модели в конфигурации
- **WHEN** конфигурация вызова меняет модель решающей оценки на другую
- **THEN** кандидаты, ранее оценённые прежней моделью, запрашиваются
  заново, а не берутся из кэша прежней модели

### Requirement: Обработка 429 при батчевой оценке
Получение HTTP 429 при вызове решающей LLM MUST трактоваться как
временная, а не фатальная ошибка. Фильтратор MUST выполнять повторную
попытку с учётом заголовка `Retry-After`, не прерывая обработку остальных
кандидатов батча и не пропуская документ без оценки молча.

#### Scenario: Провайдер вернул 429
- **WHEN** вызов решающей оценки получает HTTP 429
- **THEN** фильтратор выжидает интервал из `Retry-After` (или пейсер по
  умолчанию, если заголовка нет) и повторяет запрос, не завершая работу
  аварийно

### Requirement: Негатив-фильтр каталога — вето после порога
После применения порога 7.5 фильтратор MUST проверить оставшиеся
документы на совпадение с negative-regex объекта и MUST исключить
совпавшие из итогового набора. Негатив-фильтр MUST применяться после
решающей оценки, не вместо неё и не до неё.

#### Scenario: Документ прошёл порог, но попал под негатив-фильтр
- **WHEN** документ получил оценку ≥7.5, но его текст matches negative-regex
  объекта
- **THEN** документ исключается из итогового набора

### Requirement: Итог отбора пишется в agent_2_relevant_documents
Документы, прошедшие порог 7.5 и негатив-фильтр, MUST записываться в
`agent_1_v5.agent_2_relevant_documents` строками `(id_object,
id_clean_post, llm_score, selected_at)`. Таблица MUST содержать только
итог — документ, не прошедший порог или отсеянный негатив-фильтром,
MUST NOT попадать в неё ни в каком виде (ни отдельным статусом, ни
пустой строкой). Таблица MUST NOT содержать полей, привязывающих
документ к драйверу, упоминанию или KR.

#### Scenario: Документ прошёл весь конвейер
- **WHEN** документ получил оценку ≥7.5 и не попал под негатив-фильтр
- **THEN** в `agent_2_relevant_documents` появляется строка с этим
  `id_object`, `id_clean_post`, оценкой и временем отбора

#### Scenario: Документ не прошёл порог или попал под вето
- **WHEN** документ получил оценку <7.5, либо оценку ≥7.5, но попал под
  негатив-фильтр
- **THEN** для этой пары (`id_object`, `id_clean_post`) строка в
  `agent_2_relevant_documents` не создаётся

### Requirement: Отбор по объектам независим — связь объект↔документ M:N
Фильтратор MUST обрабатывать каждый объект наблюдения независимо: набор
кандидатов, порог, негатив-фильтр и итоговый результат для одного
объекта MUST NOT зависеть от того, был ли документ уже отобран (или
отвергнут) для другого объекта. Один документ MUST иметь возможность
одновременно входить в итоговые наборы нескольких разных объектов, и
фильтратор MUST NOT дедуплицировать документ глобально по корпусу —
только в рамках отбора одного объекта.

#### Scenario: Документ релевантен двум объектам одновременно
- **WHEN** документ проходит порог 7.5 и негатив-фильтр для объекта A и
  независимо проходит их же для объекта B
- **THEN** документ входит в итоговый набор обоих объектов, ни один из
  результатов не подавляется тем, что документ уже отобран для другого
  объекта

#### Scenario: Документ отвергнут для одного объекта, принят для другого
- **WHEN** документ не проходит порог или попадает под негатив-фильтр
  объекта A, но проходит их для объекта B
- **THEN** документ отсутствует в итоговом наборе объекта A и присутствует
  в итоговом наборе объекта B — обработка объекта A не блокирует и не
  влияет на результат объекта B

### Requirement: Регрессионный тест на эталоне — условие приёмки
Прогон фильтратора на эталоне (`experiments/retrieval_eval/data/labels_v2.jsonl`) MUST давать полноту (recall) не ниже 70% в среднем
по объектам, размеченным в эталоне. Сборка, не проходящая этот порог,
MUST считаться не готовой к приёмке.

#### Scenario: Прогон регрессионного теста перед приёмкой
- **WHEN** реализация фильтратора прогоняется на эталоне `labels_v2.jsonl`
- **THEN** средняя полнота по объектам эталона составляет не менее 70%,
  иначе change не принимается
