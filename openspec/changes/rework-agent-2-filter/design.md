## Context

Замер ретрива (`docs/architecture/retrieval_research_report.md`, 1318
размеченных документов, эталон `experiments/retrieval_eval/
data/labels_v2.jsonl`) закрыл вопрос конструкции отбора. Рабочий прототип
`experiments/retrieval_eval/filter_agent.py` реализует каналы и
объединение, но отсечку по разрыву в распределении, которую сам же
прототип помечает как непроверенную и уже замененную в замерах на
LLM-рубрику (см. шапку файла и `retrieval_research_report.md`, раздел 5).

Каталог объектов приходит готовым от внутреннего агента банка
(`docs/architecture/observation_objects_context.md`) — старая роль
Агента 2 (генерация объектов из бизнес-цели) снята. Агент 2
переопределяется: было — генератор объектов, стало — фильтратор
документов под готовый объект. Старый `agents/agent_2/` архивируется, не
удаляется (код используется до тех пор, пока не понадобится для справки).

Решения пользователя, зафиксированные 2026-08-06 (см. проект-память):
фильтратор = новый агент 2 (та же нумерация); решающая LLM вызывается
через OpenClaw, не хардкодится; пересчёт корпуса асимметричной моделью
эмбеддингов отложен; KR — не забота агента 2, катал­ог и негатив-фильтр
остаются на уровне объекта, без привязки к KR; извлечение драйверов и
«Упоминаний» — забота будущего, отдельного агента, читающего результат
агента 2, а не самого агента 2 (см. D10 — целевая таблица результата
решена как отдельная M:N-таблица без понятия драйвера).

## Goals / Non-Goals

**Goals:**
- Перенести конструкцию из `filter_agent.py` в постоянный код агента 2:
  два канала → объединение → LLM-оценка по рубрике → порог 7.5 →
  негатив-фильтр как вето.
- Добавить `search_description` в контракт объекта и использовать его,
  а не название, как текст запроса векторного канала.
- Заменить решающую отсечку (разрыв в распределении) на LLM-рубрику
  0–10, порог 7.5, с кэшем по ключу (объект, документ, модель) и
  устойчивой обработкой 429.
- Вызывать решающую LLM через OpenClaw (паттерн
  `agent_1/label_kr_worker.py`), не через прямой OpenRouter API.
- Регрессионный тест на эталоне `labels_v2.jsonl` как условие приёмки:
  полнота ≥70%.
- Архивировать старый `agents/agent_2/` без удаления.

**Non-Goals:**
- Извлечение драйверов и заполнение таблицы «Упоминания» (`id_драйвера`
  и всё, что с ним связано) — забота отдельного, будущего агента.
  Агент 2 про драйверы не знает вообще и в его схему они не входят.
- Всё, что связано с KR (Key Results): связь объект↔KR, вес, полярность,
  KR-специфичные негатив-фильтры/веса источников/окно дат — не забота
  агента 2. Каталог объектов и его поля (включая негатив-фильтр и веса
  источников) остаются свойством самого объекта, без KR-измерения.
- Пересчёт корпуса асимметричной моделью эмбеддингов — отдельный change.
- Выбор конкретной модели (Opus/Sonnet) для решающей оценки — решается
  конфигурацией вызова OpenClaw, не фиксируется в коде агента.
- Агент-экстрактор драйверов, оценщики влияния, оркестратор — отдельные
  changes (см. `pipeline_v5_context.md`).
- Исправление известных слепых зон методики (объект 8 не берётся ничем,
  9% положительных документов мимо кандидатов, регексы объектов 2–10 —
  реконструкция) — документируются, не чинятся в рамках этого change.

## Decisions

### D1. Каналы складываются, а не пересекаются
Лексический канал (regex ключевых слов каталога) и векторный канал
(эмбеддинг `search_description`, top-500) объединяются через `|`, не `&`.
Замер: цепочка «И» проиграла ключевым словам на 8 объектах из 8, на
«Инцидентах» — 1.4% против 61.4% у одного вектора
(`retrieval_research_report.md`, раздел 4.2). Архитектура банка
предполагала пересечение — это сознательное расхождение, основанное на
измерении, не переоткрывается.

### D2. Запрос векторного канала — `search_description`, не название
Название объекта как запрос даёт recall@500 64.6%, описание — 76.9%
(раздел 4.1 отчёта). Разрыв не объясняется длиной запроса (проверено на
асимметричной модели с раздельным кодированием запроса/документа).
Отсюда: `search_description` — обязательное поле контракта объекта
(`proposal_search_description.md`), не опциональное улучшение.

### D3. Граница — LLM-рубрика, порог 7.5
Отсечка по разрыву в косинусе даёт 70.7% полноты / 39.9% точности / 138
документов и фактически вырождается в фиксированное K (детектор обрыва
упирался в защитный минимум на позициях 20–43). LLM-рубрика по словесной
шкале 0–10 даёт 76.5% / 93.3% / 44 документа — и порог 7.5 воспроизведён
независимо двумя моделями (Opus, Sonnet), потому что шкалу задают слова
рубрики, а не геометрия эмбеддинга. `adaptive_cutoff()` из прототипа
удаляется полностью, не оставляется как fallback — обоснование замены
уже задокументировано в самом прототипе.

### D4. Негатив-фильтр каталога — вето после порога
Применяется к объединённому и уже отфильтрованному по порогу набору, не
до него: дешёвый и предсказуемый способ убрать шум без риска зарезать то,
что поймала LLM-оценка. Соответствует прототипу (`filter_agent.py`,
шаг 4) и разделу 3 брифа.

### D5. Решающая LLM — вызов через OpenClaw, не прямой OpenRouter
Прототип бьёт напрямую в OpenRouter API (`embed_v5.openrouter_embed`,
`OPENROUTER_API_KEY`). Для батчевой рубричной оценки переходим на паттерн
`agent_1/label_kr_worker.py`: `--openclaw-cmd`/`--agent-id`/`--model`/
`--thinking`, рейт-лимит на вызовы в минуту, таймаут на агента. Модель
эмбеддингов (векторный канал) прямой вызов API не меняет — вопрос был
только про решающую LLM-оценку по рубрике.
Альтернатива (оставить прямой OpenRouter для скорости реализации)
отклонена явным решением пользователя: модель/бюджет — вопрос денег,
которым управляет OpenClaw-обвязка, не код агента.

### D6. Кэш решающей оценки — ключ (объект, документ, модель)
Грабля из прототипа/брифа: кэш без модели в ключе молча переиспользует
чужие оценки. Ключ кэша фиксируется тройкой с самого начала, не
добавляется post-factum.

### D7. Обработка 429 — пейсер и уважение Retry-After
429 — временная ошибка, не фатальный сбой (грабля брифа: одна из
измеренных проблем — 429 был принят за фатальную ошибку). Батчевая
оценка кандидатов реализует бэкофф с учётом заголовка `Retry-After`, не
падает и не пропускает документ молча.

### D8. `hnsw.ef_search` — через `set_config()`
`SET hnsw.ef_search = %s` синтаксически не работает с параметризацией
(`SET` принимает только литералы) — грабля уже поймана в
`run_eval.set_ef_search`. Новый код переиспользует эту функцию, не
переизобретает.

### D9. Старый агент 2 — архивируется, не удаляется
`agents/agent_2/*` (промпт, `AGENTS.md`, `SOUL.md`, `TOOLS.md` и т.д.)
перемещается в архивное состояние (аналогично паттерну
`openspec/changes/archive/`) с пометкой о причине и дате. Новый агент 2
заводится на его месте под тем же номером. Обоснование — явное решение
пользователя: не сносить, только заархивировать.

### D10. Три таблицы в схеме `agent_1_v5` — каталог, кэш, результат
Целевая таблица решена (2026-08-06): всё лежит в одной схеме
`agent_1_v5`, рядом с `raw_posts`/`clean_posts` — пользователь явно
попросил «чтобы всё в одном месте лежало, так нагляднее». Три новые
таблицы:

```
agent_1_v5.observation_objects
  id_object          bigint PK
  label              text
  aliases            text[]
  keywords           text          -- regex, канал включения
  negative_filter    text          -- regex, вето
  source_weights     jsonb
  search_description text
  query_embedding    vector(1024)
  created_at, updated_at

agent_1_v5.agent_2_llm_scores        -- кэш решающей оценки (D6)
  id_object      FK -> observation_objects
  id_clean_post  FK -> clean_posts
  model          text
  score          numeric
  scored_at      timestamptz
  PRIMARY KEY (id_object, id_clean_post, model)

agent_1_v5.agent_2_relevant_documents  -- итог фильтратора, M:N
  id_object      FK -> observation_objects
  id_clean_post  FK -> clean_posts
  llm_score      numeric
  selected_at    timestamptz
  PRIMARY KEY (id_object, id_clean_post)
```

`agent_2_relevant_documents` содержит только документы, прошедшие порог
7.5 и негатив-фильтр — это финальный результат агента 2, не кандидаты.
Строк с одним и тем же `id_clean_post` и разными `id_object` может быть
сколько угодно (M:N) — таблица именно junction, без единственного
`object_id` на документе. Никакого понятия драйвера или упоминания
здесь нет: связывание с драйверами — работа будущего агента, который
читает эту таблицу как вход, join'ится на `clean_posts` за текстом и
сам решает, что с этим делать. Это прямое следствие решения «КР и
драйверы — не забота агента 2» (2026-08-06).

Альтернатива (отдельная схема `agent_2` вместо `agent_1_v5`) отклонена
явным запросом пользователя — совместное расположение важнее
формальной границы владения по агентам, тем более что агент 2 и так
только читает `clean_posts` из той же схемы.

## Risks / Trade-offs

- [Будущий агент драйверов ожидает другую форму данных, чем
  `agent_2_relevant_documents`] → таблица нарочно минимальна (M:N
  объект↔документ, без драйвера/упоминания) именно потому, что формат
  выхода для драйверного агента ещё не спроектирован; переделка на
  уровне *схемы* дешевле, чем если бы агент 2 уже писал в чужой,
  недоопределённый контракт («Упоминания» с `id_драйвера`).
- [429 при батчевой LLM-оценке большого числа кандидатов] → пейсер +
  Retry-After (D7); без этого прогон на реальном каталоге объектов упадёт
  так же, как ловилось в экспериментах.
- [Кэш решающей оценки без модели в ключе] → ключ фиксирован тройкой с
  начала (D6), урок уже стоил времени в эксперименте.
- [LLM-рубрика проверена на 4 объектах из 8 (Opus) и 2 из 8 (Sonnet)] →
  регрессионный тест считает полноту по всем объектам эталона; если
  полнота объекта вне проверенных четырёх окажется существенно ниже
  70%, это сигнал чинить рубрику/промпт, а не повод откатывать
  конструкцию целиком.
- [Объект 8 «Корпоративное внедрение GenAI» не берётся ничем — 63.4%
  лучшей моделью] → известное ограничение формулировки объекта, не
  дефект фильтратора; документируется как принятый риск, не в скоупе
  фикса.
- [9% положительных документов не попадают в кандидаты вообще] →
  недостижимо текущей конструкцией (глубина 500 у обоих каналов не
  покрывает их); отдельное расследование вне скоупа, фиксируется как
  известный потолок полноты (~70% сквозной, не 76.5%).
- [Регексы объектов 2–10 — реконструкция, не оригиналы каталога] →
  используются как есть; когда банк пришлёт настоящие ключевые слова —
  замена конфигурации, не кода.
- [OpenClaw как единственная точка вызова LLM] → если OpenClaw
  недоступен/меняет интерфейс, батчевая оценка блокируется целиком;
  смягчается тем, что тот же паттерн уже используется в проде
  `agent_1/label_kr_worker.py`, то есть путь проверенный, не новый риск.

## Migration Plan

1. Переместить `agents/agent_2/*` в архив (без удаления), зафиксировать
   дату и причину.
2. Создать DDL для `agent_1_v5.observation_objects`,
   `agent_1_v5.agent_2_llm_scores`, `agent_1_v5.agent_2_relevant_documents`
   (D10).
3. Завести пакет нового агента 2 (по аналогии с
   `agents/agent_1/src/agent_1/`), перенести и адаптировать
   `filter_agent.py`/`patterns.py`/`queries.py` из
   `experiments/retrieval_eval/`.
4. Добавить `search_description` в контракт объекта наблюдения
   (`observation_objects.search_description`).
5. Реализовать оба канала, объединение, LLM-рубрику через OpenClaw (D5),
   кэш в `agent_2_llm_scores` (D6), пейсер 429 (D7), негатив-вето (D4),
   запись итога в `agent_2_relevant_documents` (D10).
6. Подключить регрессионный тест на `labels_v2.jsonl` (полнота ≥70%) как
   условие приёмки change.

Rollback: старый агент 2 не удалён (D9) — при отказе от фильтратора
пайплайн можно переключить обратно на архивную версию.
