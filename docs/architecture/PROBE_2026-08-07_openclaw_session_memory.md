# Промпт для OpenClaw: как session-key соотносится с памятью агента

**Дата:** 2026-08-07
**Контекст:** агент 2 вызывает решающую LLM-оценку через `openclaw agent
--agent agent_2 --session-key <уникальный на пакет> --message ...`
(`agents/agent_2/src/agent_2/llm_scoring.py`). Каждый вызов получает
СВОЙ уникальный `session-key` (по объекту+номеру пакета), по образцу
`agent_1/label_kr_worker.py`. Неясно: это осознанная изоляция сессий
друг от друга, или у неё есть побочный эффект на MEMORY.md/DREAMS.md
агента — и вообще, что реально означает `--session-key` в OpenClaw.
**Режим:** сначала только чтение/документация, потом — наблюдение за
файлами памяти агента 2 (тоже без записи в них руками).

Всё ниже до конца файла — текст, который отдаётся OpenClaw как есть.

## ЗАДАЧА

Ответить на три вопроса. Не гадать по общим впечатлениям — там, где
можно проверить фактом (флаг в `--help`, реальный файл на диске,
реальный лог сессии), проверить именно так.

**Вопрос 1.** Что документация/`--help` самого OpenClaw говорят про
`--session-key`: он привязан к истории диалога (контекст предыдущих
сообщений с тем же ключом продолжается), или это только метка для
логов/дедупликации, не влияющая на память агента?

**Вопрос 2.** Есть ли у OpenClaw механизм консолидации памяти («dreaming»
— судя по авто-блоку `<!-- openclaw:dreaming:deep:start -->` в
`agents/agent_1/DREAMS.md` и `agents/agent_2/DREAMS.md`, что-то подобное
есть). Если да: он смотрит на ВСЕ сессии агента (включая
уникально-одноразовые, как у скоринга агента 2), или только на
какие-то отмеченные/долгоживущие?

**Вопрос 3 (эмпирика).** Реально ли за серию из N узких одноразовых
вызовов скоринга что-то попадает в `MEMORY.md`/`DREAMS.md`/`memory/`
агента 2 — или эти файлы остаются нетронутыми, потому что каждый вызов
изолирован и в них просто нечему конденсироваться.

### Ограничения

- Шаги 1–2 (документация) — chтение файлов/`--help`, ничего не менять.
- Шаг 3 (эмпирика) — только читать `agents/agent_2/MEMORY.md`,
  `agents/agent_2/DREAMS.md`, `agents/agent_2/memory/*` до и после;
  **не писать в них руками** — интересен факт, изменяет ли их сам
  OpenClaw, а не подстроенный результат.
- Не запускать новые вызовы скоринга специально ради этого зонда —
  используй как «до/после» ближайший реальный прогон регрессии
  (`agents/agent_2/scripts/run_regression.py`), если он идёт или только
  что прошёл. Если прогона в обозримое время не будет — так и напиши,
  этот вопрос останется открытым до следующего реального прогона.

## БЛОК A — документация OpenClaw

```bash
openclaw --help
openclaw agent --help
```

Поищи файлы документации рядом с установкой (сама установка —
`/root/.hermes/node/bin/openclaw` или где покажет `which openclaw`):

```bash
find "$(dirname "$(which openclaw)")/.." -maxdepth 3 \
  \( -iname "README*" -o -iname "*.md" -o -iname "CHANGELOG*" \) 2>/dev/null
```

Если есть подкоманды вида `openclaw docs`, `openclaw help session`,
`openclaw help memory` — тоже посмотреть.

## БЛОК B — до прогона (снимок)

```bash
echo "--- MEMORY.md ---"
cat agents/agent_2/MEMORY.md 2>/dev/null || echo "(нет файла)"
echo "--- DREAMS.md ---"
cat agents/agent_2/DREAMS.md 2>/dev/null || echo "(нет файла)"
echo "--- memory/ ---"
ls -la agents/agent_2/memory/ 2>/dev/null || echo "(нет папки)"
```

Сохрани вывод как снимок «до».

## БЛОК C — после прогона (тот же снимок)

После того как отработает ближайший реальный прогон `run_regression.py`
(десятки/сотни вызовов скоринга с уникальными `session-key`), повтори
ровно те же три команды из блока B. Сравни построчно с «до».
