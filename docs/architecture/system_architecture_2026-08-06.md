# Архитектура системы v6 (2026-08-06)

**Источник:** drawio-диаграмма «Архитектура v6», присланная пользователем
2026-08-06 (`докs/architecture/арх_системы.xml` — исходник сохранён в
репозитории пользователем, в отличие от прежних материалов). Перенесена
сюда для полноты и читаемости без картинки.

**Статус:** канон архитектуры, приходит на смену пайплайновому описанию
из `pipeline_v5_context.md` (плоский список из 6 агентов) и частично
дополняет `system_architecture_2026-07-31.md`. Смежные документы:
`observation_objects_context.md` (методика и контракт объекта
наблюдения — контракт в этой диаграмме расширяется, см. раздел 11),
`retrieval_research_report.md` и `proposal_search_description.md`
(механика агента-фильтратора — не меняется этим документом).

**Что изменилось принципиально:** пайплайн v5 был одной линией из 6
агентов под одним оркестратором. В v6 — два независимых доменных
контура (новости и отзывы), каждый со своим суб-оркестратором и циклом
critique (executor ⇄ judge), плюс отдельный контур саморазвития системы
(рефлексия, золотой набор, версионируемые правила). Ветка отзывов
целиком новая — её не было ни в одном прежнем документе.

---

## 1. Общая схема

```
                          Объекты наблюдения (вход)
                                    │
                          Корневой оркестратор
                          ┌─────────┴─────────┐
                 Суб-оркестратор          Суб-оркестратор
                 · новости                · отзывы
                 (executor ⇄ judge)       (executor ⇄ judge)
                          │                       │
                 ветка новостей            ветка отзывов
                 события → драйверы        продукты → аспекты
                          │                       │
                          └─────────┬─────────────┘
                                Хранилища
                                    │
                          слияние в «Драйверы»
                          (дедуп, флаги противоречий)
                                    │
                          ⑥ Агент-копирайтер
                                    │
                          Выход: драйверы (направление × сила),
                          аспектная картина, примеры

Параллельно — КОНТУР САМО-РАЗВИТИЯ:
  Журнал запусков → Агент-рефлексии → «Опыт»/правила (версии)
                          │
                  Куратор золотого набора → Золотой набор + метрики
```

## 2. Вход: объекты наблюдения

Контракт объекта на этой диаграмме шире, чем в `observation_objects_context.md`:

> связь с КР, алиасы, ключевые слова, **продукты и SKU**, **конкуренты**,
> площадки, веса источников

Поля «продукты и SKU» и «конкуренты» — новые, их не было в контракте
раздела 2 `observation_objects_context.md` (там были: id, название,
связь с KR, вес, алиасы, ключевые слова, негатив-фильтр, веса
источников). Судя по месту в схеме, это поля под ветку отзывов
(сравнение продукта с конкурентами). **Точный тип/формат этих полей не
угадываю** — контракт нужно уточнить у пользователя так же, как в своё
время `search_description`.

## 3. Корневой оркестратор

- расписание, приоритеты объектов наблюдения;
- запуск и контроль доменных веток;
- слияние веток: дедуп драйверов, флаги противоречий;
- фиксация версии правил «Опыта» на прогон;
- shadow-run по запросу агента-рефлексии.

Ниже него — два суб-оркестратора (новости, отзывы), у каждого одинаковый
паттерн: **Агент-executor** + **Агент-judge** (⟳ — читает «Опыт» на
старте), цикл «запуск → оценка → доработка» с лимитом перезапусков.

## 4. Ветка новостей · события → драйверы

Уровни агентов помечены буквами (расшифровка — раздел 9).

**① Пайплайн сбора новостей** (детерминированный, без LLM):
- Parsers360 API: выгрузка новостей;
- regex-фильтры шума и языка;
- дедупликация: MinHash + Левенштейн;
- эмбеддинги: Text Embeddings 3 Large.

Совпадает с пайплайном сбора из `system_architecture_2026-07-31.md`
(раздел 3) — без изменений.

**② Агент-фильтратор** [A, ⟳]:
- семантический поиск по объекту;
- ключевые слова + негатив-фильтр;
- отбор релевантных чанков новостей.

Это тот самый агент, под который уже заведён `openspec/changes/
rework-agent-2-filter/`. Номер **②** в этой диаграмме подтверждает
решение пользователя от 2026-08-06 «фильтратор = агент 2» — расхождений
с уже принятым change нет.

**③ Агент-экстрактор драйверов** [A, ⟳]:
- GliNER + GliREL: сущности и связи;
- драйверная модель;
- фильтрация кандидатов агентом.

**④ Агент-оценщик направления** [B, ⟳]:
- few-shot / ML-модель;
- направление влияния на объект наблюдения.

**⑤ Агент-оценщик силы** [B, ⟳]:
- few-shot / ML-модель;
- сила влияния: низкая / средняя / высокая (батчи).

Раздельные оценщики направления и силы соответствуют «Агенту-оценщику
направления влияния» и «Агенту-оценщику силы влияния» из
`pipeline_v5_context.md` (там же — Агенты 6 и 7 старой нумерации);
здесь они встроены внутрь ветки новостей, а не отдельные top-level
агенты пайплайна.

## 5. Ветка отзывов · продукты → аспекты (новое)

Полностью новый контур — не описан ни в одном прежнем документе.
Паттерн суб-оркестратора тот же (executor ⇄ judge, цикл с лимитом).

**① Пайплайн сбора отзывов** (детерминированный):
- Parsers360 API: выгрузка отзывов (по объекту наблюдения);
- верификация (берём то, что подтверждено);
- дедупликация.

**Агент-аналитик метрик и аномалий** [A, ⟳]:
- срезы: объект × продукт × площадка × регион × версия;
- нормировка на веса площадок (авторитетность площадки);
- продукт vs конкуренты (статистика);
- аномалии (выделить) и тренды (предсказать).

**Агент-экстрактор аспектов (ABSA)** [C, ⟳]:
- аспект — составная часть продукта;
- пары «аспект → тональность» по проблемным срезам;
- словарь аспектов для «Опыта»;
- сверка с оценкой 1–5 как с приором.

**⑤ Агент выделения драйверов** [A, ⟳]:
- доля × вес × динамика;
- драйвера;
- ретроспектива.

Пишет в «Драйверы» через отдельный **промоут**-путь (пунктирная красная
связь на диаграмме): драйверы из отзывов (направление + сила), топ-N
примеров → «Примеры упоминаний». Это отдельная от ветки новостей запись
в те же итоговые витрины, не слияние на уровне самого агента.

Номер **⑤** используется в обеих ветках для разных агентов (оценщик силы
в новостях, выделение драйверов в отзывах) — похоже на неточность самой
диаграммы, не переносить как значимое совпадение.

## 6. Слияние и выход

Корневой оркестратор сливает обе ветки в «Драйверы»: дедуп, флаги
противоречий (красная пунктирная связь от обоих суб-оркестраторов к
«Драйверам»).

**⑥ Агент-копирайтер** [A, ⟳]:
- сводит драйверы, аспекты и примеры;
- метч по КР.

**Выход:** драйверы (направление × сила), аспектная картина, примеры.

## 7. Хранилища

| Хранилище | Заполняется |
|---|---|
| Vector DB · новости | пайплайн сбора новостей (эмбеддинги + метаданные) |
| Vector DB · отзывы | пайплайн сбора отзывов |
| Объекты мониторинга | вход системы |
| Примеры упоминаний | агент-фильтратор (запись), копирайтер (чтение), промоут из отзывов |
| Отзывы | пайплайн сбора отзывов |
| Метрики отзывов | агент-аналитик метрик и аномалий |
| Сравнение с конкурентами | агент-аналитик метрик и аномалий |
| Long-term memory · словари | агент-экстрактор аспектов (словарь аспектов) |
| Драйверы | слияние веток (оркестратор), агент выделения драйверов (отзывы) |
| Аспекты и мнения | агент-экстрактор аспектов (ABSA) |

**Не установлено соответствие** с 13-табличной схемой v5 из
`pipeline_v5_context.md` (`source, raw_posts, clean_posts, Key_results,
cluster, kr_cluster_match, gliner_entities, entity_canonical,
driver_instance, driver_mention, kr_report, processing_jobs,
post_kr_processing`). Диаграмма называет хранилища содержательно
(«Vector DB · новости»), а не именами таблиц БД — соответствие имён
(например, «Vector DB · новости» = `clean_posts`? «Объекты мониторинга» =
новая таблица от банка?) нужно сверять отдельно, не додумываю.

**Также не решено**: показанная на схеме «Vector DB» как отдельный
цилиндр — это по-прежнему pgvector внутри Postgres (решение «путь A» из
`pipeline_v5_context.md`, раздел 4: «отдельная векторная БД отклонена»),
или архитектура теперь предполагает физически отдельный векторный
сервис. Диаграмма рисует хранилища единообразно как цилиндры независимо
от физической реализации — до отдельного подтверждения считаю, что
принятое решение «путь A» не отменено.

## 8. Контур само-развития (новое)

Отдельный блок системы, работающий параллельно доменным веткам:

- **Журнал запусков** — фиксирует ход прогона (принимает выходы от
  корневого оркестратора).
- **Агент-рефлексии**:
  - валидация выходов от агентов;
  - shadow-run на золотом наборе;
  - калибровка весов источников и порогов;
  - промоут в правила — **только если метрика не хуже**.
- **«Опыт» и правила (версии)** — читается всеми агентами на старте
  (⟳), пополняется агентом-рефлексии; версия фиксируется на прогон
  (принцип воспроизводимости — прогон не может видеть более новую
  версию правил, чем та, с которой стартовал).
- **Золотой набор + метрики** — эталон для shadow-run, метрики до/после
  при промоуте правил.
- **Куратор золотого набора**:
  - вход: подтверждённые кейсы и флаги противоречий из «Драйверов»;
  - → кандидаты в эталоны.

Это полноценный мета-слой самообучения системы — ничего подобного не
было ни в `pipeline_v5_context.md`, ни в `system_architecture_2026-07-31.md`.
Не пересекается с уже принятыми решениями по агенту-фильтратору
(`rework-agent-2-filter`), но задаёт для него будущий контекст: агент 2
тоже, по-видимому, должен уметь читать/писать свою секцию «Опыта» (⟳
стоит на его иконке) — это не было предусмотрено в уже сделанном
openspec-change и требует отдельного решения, не добавляю туда
самовольно.

## 9. Уровни агентов и профили скорость/качество (новое)

Каждый агент помечен буквой важности:

| Уровень | Значение |
|---|---|
| ●A | ядро, не отключать |
| ●B | качество, можно заменить эвристикой |
| ●C | опция, отключается первой |

Профили запуска всей системы:

| Профиль | Состав | Время |
|---|---|---|
| **FULL · Качество** | все агенты + циклы критиков (A+B+C) | базовый уровень (100%) |
| **BALANCED** | без (C) | −15…−25%* |
| **FAST** | без (B) | −35…−45%* |

Расстановка по веткам:
- Новости: ② фильтратор — A; ③ экстрактор драйверов — A; ④ оценщик
  направления — B; ⑤ оценщик силы — B.
- Отзывы: агент-аналитик метрик — A; агент-экстрактор аспектов (ABSA) —
  **C**; агент выделения драйверов — A.
- ⑥ Копирайтер — A. Агент-рефлексии и куратор золотого набора без
  буквенной пометки на диаграмме (относятся к контуру саморазвития, не
  к профилям FULL/BALANCED/FAST доменных веток).

## 10. Легенда управления (условные обозначения диаграммы)

| Обозначение | Цвет | Значение |
|---|---|---|
| ━━ | фиолетовый | управление: задание ⇆ результат (цикл) |
| ── | серый | данные: чтение / запись витрин |
| ╌╌ | оранжевый | само-развитие |
| ╌╌ | красный | драйверы: запись и слияние веток |
| ⟳ | — | агент читает свою секцию «Опыта» на старте и пишет итог в конце |

## 11. Открытые вопросы и расхождения с прежними документами

Ничего из перечисленного не додумано — фиксирую как есть, для
последующего уточнения у пользователя.

1. **Ветка отзывов целиком новая.** Не описана ни в
   `pipeline_v5_context.md`, ни в `observation_objects_context.md`, ни в
   `system_architecture_2026-07-31.md`. Не в скоупе уже принятого change
   `rework-agent-2-filter` — отдельная будущая работа.
2. **Контракт объекта наблюдения расширяется** полями «продукты и SKU» и
   «конкуренты», которых нет в `observation_objects_context.md`
   (раздел 2). Формат полей не определён.
3. **«Vector DB» на диаграмме** — не подтверждено, остаётся ли это
   pgvector внутри Postgres (принятое решение «путь A») или подразумевает
   отдельный векторный сервис.
4. **Хранилища диаграммы не сведены** с 13-табличной схемой v5
   (`schema_v5.dot`) — соответствие имён не установлено.
5. **Мета-контур саморазвития** (агент-рефлексии, куратор золотого
   набора, версионируемый «Опыт») — новая концепция, не описана ни в
   одном существующем change/spec. В частности неясно, должен ли агент 2
   (фильтратор) читать/писать «Опыт» (⟳ на его иконке) — это не заложено
   в уже сделанный `openspec/changes/rework-agent-2-filter/design.md`.
6. **Номер ⑤ дублируется** между веткой новостей (оценщик силы) и
   веткой отзывов (агент выделения драйверов) — вероятная неточность
   самой диаграммы, не переносить в спеки как значимое совпадение.
7. **Уровни агентов (A/B/C) и профили (FULL/BALANCED/FAST)** — новая
   операционная концепция, не пересекается с уже принятыми решениями по
   фильтратору, но потенциально влияет на его конфигурацию в проде
   (агент помечен уровнем A — «ядро, не отключать»).
