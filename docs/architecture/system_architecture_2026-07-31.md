пользователем 2026-07-31. Перенесены сюда, чтобы не зависеть от чата:

## 1. Контракт системы

### Вход: список объектов наблюдения

| Поле | Тип |
|---|---|
| id объекта | int |
| Объект наблюдения | str |
| Связь с КР | str |
| Вес→КР | float |
| Алиасы | list[str] |
| Ключевые слова | list[str] |
| Негатив-фильтр | list[str] |
| Веса источников | json `{'Источники': int}` |

### Выход: драйверы

| Поле | Тип |
|---|---|
| id драйвера | int |
| id объекта | int |
| Объект наблюдения | str |
| Драйвер (инсайт) | str |
| Влияние на объект | Enum[позитивное, нейтральное, негативное] |
| Сила влияния | Enum[низкая, средняя, высокая] |
| Число упоминаний | int |

### Выход: примеры упоминаний

| Поле | Тип |
|---|---|
| id упоминания | int |
| id драйвера | int |
| id объекта | int |
| Источник | str |
| Опубликовано | timestamptz |
| Ссылка | str |
| Контекст | str |

## 2. Хранилища

- **Векторная БД** — эмбеддинги новостей плюс метаданные.
- **Реляционная БД** — таблицы «Драйверы», «Примеры упоминаний»,
  «Объекты мониторинга»; поля совпадают с контрактом системы.
- **Long-term memory** — читается и пишется агентом-экстрактором.

---

## 3. Пайплайн сбора данных

**Вход:** пороги схожести для дедупликации.
**Выходы:** эмбеддинги и метаданные в Vector DB; характеристики датасета —
оркестратору.

Шаги:

1. **API-запрос к Parsers360** — `POST https://parsers360.ru/api/parametrized`.
   Параметры: `token` (обязательный), `interval` (обязательный, промежуток
   выгрузки), `sources` (необязательный, несколько источников через `;`;
   не указывать для выгрузки по всем), `summary` (краткая выжимка),
   `companies` (упоминаемые компании и предложения с упоминаниями).
2. **Фильтрация шума и нерусскоязычных новостей** через regex.
3. **Дедупликация** — оценка схожести через MinHash и расстояние
   Левенштейна. Порог схожести подбирается эмпирически.
4. **Векторизация.** Энкодер: **Text Embeddings 3 Large**.

## 4. Агент-фильтратор

ReAct-агент. По объекту мониторинга находит и фильтрует новости.
Вызывается **отдельно для каждого объекта**.

**Вход:** ID объекта мониторинга, доп. инструкции от оркестратора.
**Выходы:** релевантные новости (запись в «Примеры упоминаний»);
характеристики выбранных чанков — оркестратору.

**Тулы:** запись в БД, чтение из БД, семантический поиск, фильтр по
ключевым словам, негатив-фильтр.

**Алгоритм.** Агент получает ID объекта, читает его название в таблице.
Выполняет запрос в векторную БД, достаёт наиболее релевантные новости.
Отобранные новости проходят фильтры по ключевым словам и негатив-фильтры.
Результат пишется в «Примеры упоминаний», характеристики отобранного
уходят оркестратору.

Если оркестратора не устроит ответ, он может варьировать словари ключевых
слов и негатив-фильтров, менять параметры поиска и дописывать инструкции.

---

## 5. Агент-экстрактор драйверов

ReAct-агент. Пошагово выделяет драйверы. Вызывается **отдельно для
каждого объекта**.

**Вход:** ID объекта мониторинга, доп. инструкции от оркестратора.
**Выходы:** примеры упоминаний; драйверы; список драйверов.

**Тулы:** запись в БД, чтение из БД, применение GliNER, применение GliREL,
применение драйверной модели.

**Алгоритм.** Для объекта достаются все примеры упоминаний (выход
предыдущего агента). Формулируются сущности и связи для GliNER и GliREL,
выполняется инференс. Полученные сущности фильтруются агентом и проходят
через драйверную модель. Результаты пишутся в «Драйверы» и дополняют
«Примеры упоминаний».

Оркестратор может дописать инструкции к драйверной модели или
скорректировать входы для GliNER/GliREL. Возможны чтение и обновление
долгосрочной памяти.

---

## 6. Агент-оценщик направления влияния

ReAct-агент. Оценивает характер влияния драйверов на объект.
Обрабатывает драйверы **пакетно**.

**Вход:** список ID драйверов с доп. инструкциями.
**Выход:** список направлений влияния.
**Тулы:** запись в БД, чтение из БД.

Реализация: few-shot prompt либо ML-модель. Оркестратор может дописать
инструкции к алгоритму определения направлений.

---

## 7. Агент-оценщик силы влияния

ReAct-агент, устроен симметрично оценщику направления: вход — список ID
драйверов с инструкциями, выход — список сил влияния, тулы — чтение и
запись в БД, обработка пакетная, реализация через few-shot prompt или
ML-модель.

---

## 8. Агент-оркестратор

Стоит поверх всех агентов; остальные агенты для него — тулы.
Концептуально состоит из двух подагентов: **executor** и **критик**
(reflector).

**Вход:** список объектов наблюдения (вход всей системы).
**Выход:** список драйверов и примеров упоминаний.
**Тулы:** запуски остальных агентов, чтение/запись в БД, прочие тулы для
оценки результатов.

Цикл по каждому агенту (зашит в промпте и скиллах):

1. Executor формирует вход и запускает агента.
2. Критик оценивает качество работы по заранее определённым правилам.
3. Если качество недостаточно — критик даёт команду перезапустить агента с
   дополнительными инструкциями (с ограничением на число перезапусков).
4. Если качество достаточно — executor запускает следующего агента.

## 9. Потоки данных между узлами

Из drawio-схемы, для чтения без картинки:

```
Объекты наблюдения ──► Оркестратор (executor ⇄ критик)
                          │
    ┌─────────────────────┼──────────────────────┬────────────────┐
    ▼                     ▼                      ▼                ▼
Пайплайн сбора    Агент-фильтратор     Агент-экстрактор    Оценщики
    │                     │              драйверов        направления/силы
    ▼                     │                   │                   │
 Vector DB ◄──────── поиск ┘                  │                   │
                          ▼                   ▼                   ▼
              Примеры упоминаний ────► Драйверы ◄─────────────────┘
                                        Long-term memory
```

Обратные связи оркестратору: порог схожести → пайплайн сбора;
характеристики датасета ← пайплайн сбора; характеристики выбранных чанков
← фильтратор; список драйверов ← экстрактор; списки направлений и сил ←
оценщики. Управляющие сигналы: «ID ОМ + доп. инструкции к фильтрам
(цикл)» → фильтратору; «ID ОМ + доп. инструкции к сущностям (цикл)» →
экстрактору; «ID драйверов + доп. инструкции» → оценщикам.

## 10. Расхождения с текущей реализацией и открытые вопросы

Зафиксировано на 2026-07-31, по ходу эксперимента по ретриву
(`experiments/retrieval_eval/`).

**Энкодер.** Схема называет Text Embeddings 3 Large. Корпус
`agent_1_v5.clean_posts` посчитан на `openai/text-embedding-3-small` с
клиентской усечкой до 1024 компонент. Относительные сравнения форм запроса
между энкодерами переносимы, абсолютный recall — нет. Пересчёт корпуса
стоит несколько долларов; решено домерить на имеющемся, пересчитать при
переходе к реализации.

**Порядок фильтров у фильтратора.** По описанию ключевые слова
применяются *после* векторного поиска, то есть цепочка работает
пересечением. Тогда recall всей цепочки ограничен сверху recall'ом
ключевых слов: найденное вектором, но не покрытое каталогом, отсекается
следующим шагом. Данные эксперимента показывают, что у объектов-понятий
(доверие к ИИ, корпоративное внедрение, инциденты, регуляторика, лидеры
мнений) ключевые слова покрывают в разы меньше, чем есть по смыслу, — то
есть терять будет именно там. Замер считает оба варианта: цепочку через И
и объединение. **Уточняется пользователем у банка.**

**Форма запроса.** Схема предполагает запрос по *названию* объекта
(«читает его название... далее выполняется запрос в векторную БД») — самая
короткая из трёх форм, которые меряет эксперимент. Решение: делаем так,
как окажется лучше по цифрам.

**Описание объекта как поле контракта.** Во входном контракте поля
«описание» нет. Если в замере выиграет форма «описание абзацем», это поле
становится частью выхода Агента 2 (приёмника объектов) и источником для
`observation_object.embedding` — вопрос, который в черновике схемы Агента 2
стоял как `[открыто]`. Источник описания: либо банк добавляет поле, либо
оно генерируется один раз на объект из названия, алиасов и ключевых слов.

**Чанкование.** Схема говорит о «выделении релевантных чанков новостей».
Медиана `clean_content` — 709 знаков, p95 — 2908, то есть больше 95%
документов дают один чанк и резать их нечего. Нарезка осмысленна только
для длинного хвоста и делается семантически (решение пользователя,
2026-07-29).

**Ключевые слова — регексы, не текст.** В каталоге они записаны как
паттерны (`нейросет\w* сбер`). Для эмбеддинга запроса нужен шаг очистки от
regex-синтаксиса; в эксперименте он сделан вручную.
