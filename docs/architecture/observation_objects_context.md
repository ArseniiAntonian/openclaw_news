## 1. Методология: как из KR получается объект наблюдения

Из `Как_формируем_объекты_наблюдения.docx`. Пример-затравка: KR «50 тыс.
клиентов используют GenAI» — ищем не результат, а **причины**: почему
клиентов станет больше или меньше.

**Шаг 1. Разделение КР.** Метрика, целевое значение, срок и владелец
остаются атрибутами KR и в объект не переносятся. В объект уходит только
предметная часть (в примере — «GenAI»).

**Шаг 2. Определение условий.** Декомпозиция метрики на последовательные
условия достижения. Пример: клиент узнаёт о продукте → хочет подключиться
→ выбирает наш продукт, а не альтернативу → способен технически
подключиться → продолжает пользоваться.

**Шаг 3. Подготовка кандидатов.** Для каждого условия — факторы, влияющие
на его выполнение: свои продукты и их характеристики, конкуренты,
продукты-субституты, регуляторные/рыночные факторы, ключевые персоны и
т.д. (пример: GigaChat, отраслевые рейтинги, YandexGPT, open-source модели,
доверие к ИИ, лидеры мнений).

**Шаг 5. Каноникализация.** Для принятого кандидата: основное наименование,
полный перечень альтернативных написаний (рус/англ формы, аббревиатуры,
разговорные варианты), правило разрешения омонимии. Пример: «Гигачат»,
«Гигачад», «гига», «нейросеть Сбера».

**Шаг 6. Ключевые слова и негативный фильтр.** Ключевые слова — по ним
документ включается в выборку объекта. Негативный фильтр — выражения,
которые убирают новости, содержащие ключевые слова объекта, но
нерелевантные по смыслу. Пример: ключевое слово ловит «GigaChat запустил
поддержку голосового ввода», но негативный фильтр (гороскоп, юмор, мем,
«нейросеть нарисовала», «сгенерировал картинку», «кто такой», «что»)
отсекает шум.

**Шаг 7. Определение связи с KR.** Каждый объект связывается с KR через
**полярность** (направление влияния: помогает или мешает достижению KR) и
**вес** (насколько сильно — сильный конкурент и мелкий нишевый игрок оба
«мешают», но по-разному, это разводится числом).

**Важный нюанс методологии**: один и тот же объект может применяться для
**разных** KR, и при этом у него для каждого KR может быть **свой**:
негативный фильтр, веса типов источников, окно дат, связь с KR
(полярность+вес). То есть эти четыре поля — не глобальное свойство
объекта самого по себе, а свойство **пары (объект, KR)**.

## 2. Контракт данных: вход и выход

Из `Описание_полей.xlsx` — явное разделение направления потока.

### Вход к нам (от банковского внутреннего агента) — таблица «Объекты»

| Поле | Тип | Описание |
|---|---|---|
| id объекта | целое | номер объекта наблюдения |
| Объект наблюдения | текст | название фактора-драйвера |
| Связь с KR | `+` / `-` / `+-` | направление влияния объекта на цель |
| Вес→KR | целое | сила влияния объекта на цель |
| Алиасы | текст | альтернативные написания объекта |
| Ключевые слова | текст | выражения включения новости в выборку объекта |
| Негатив-фильтр | текст | выражения-исключения (отменяют попадание) |
| Веса источников | `3`/`2`/`1` по типу | значимость типов источников для объекта |
| Поисковое описание | текст | абзац о том, как выглядят новости про объект; источник текста для эмбеддинга объекта (`search_description`, добавлено `proposal_search_description.md`, 2026-07-31; обязательное поле) |

### Выход от нас (в контур банка) — таблицы «Драйверы» и «Упоминания»

**Драйверы:**

| Поле | Тип | Описание |
|---|---|---|
| id драйвера | целое | номер события-драйвера |
| id объекта | целое | к какому объекту относится событие |
| Драйвер (инсайт) | текст | суть события реального мира (факт) |
| Влияние на объект наблюдения | `позитив`/`негатив`/`нейтр` | направление эффекта события |
| Сила | `низкая`/`средняя`/`высокая` | **производная** от числа упоминаний (не независимое поле — см. п.4) |
| Упоминаний | целое | число упоминаний события за период |

**Упоминания:**

| Поле | Тип | Описание |
|---|---|---|
| id упоминания | целое | номер упоминания |
| id драйвера | целое | FK на драйвер |
| id объекта | целое | FK на объект (дублируется для удобства) |
| Источник | текст | издание-источник новости |
| Опубликовано | дата-время | время публикации |
| Ссылка | текст | прямая ссылка на новость |
| Контекст (цитата) | текст | выдержка из текста новости |

## 4. Наблюдения для будущего дизайна схемы (статус — ответы 2026-07-27)

1. **Драйвер: канонический или per-объект?** В примере одинаковый по
   смыслу инсайт («Orion soft разработала платформу...») получил два
   разных `id драйвера` для двух объектов (17, 19) — драйвер в этом
   выходном формате уже привязан к одному объекту (1:N от объекта), а не
   хранится как единая сущность со связью M:N через отдельную таблицу.
   **Не решено** («хз как лучше») — отложено до explore-сессии.
2. **«Сила» — производное поле.** Судя по описанию поля («Сила события
   по числу упоминаний (base)») и видимой корреляции в примере, это не
   независимый ввод, а бакетизация `Упоминаний`. **Отложено** («тоже
   отпусти, позже решим») — не проектировать под это сейчас.
3. **Объект↔KR — отдельная связь с собственными полями, не свойство
   объекта.** Негативный фильтр, веса источников, окно дат и связь
   (полярность+вес) могут отличаться для одного и того же объекта в
   разных KR. **Подтверждено — да**: нужна отдельная таблица-связка
   `object↔kr` с этими четырьмя полями, не единственный набор значений
   на самом объекте.
4. **Ключевые слова / негативный фильтр — это regex.** Параллель с
   `junk_categories` у Агента 1 (таблица в БД, кэш в памяти воркера,
   `compile_pattern`), полярность обратная (там отбраковывает, здесь
   включает в выборку). **Подтверждено — да**: механику compile/cache
   можно переиспользовать почти как есть.
5. **`id объекта` на Упоминаниях — НЕ лишний, исходный вывод был неверным.**
   Пользователь поправил: «Драйверы»/«Упоминания» — это не просто наша
   внутренняя схема, это **экспортный контракт обратно в контур банка**:
   банк принимает эти данные и **сам матчит объект обратно на KR,
   деобезличивая** на своей стороне. `id объекта` на каждой строке
   упоминания — обязательное поле контракта (банку нужно за что
   зацепиться для деобезличивания), не денормализация ради нашего
   удобства. **Вывод**: у нас может быть нормализованная внутренняя схема
   (канонический драйвер + M:N junction на объекты), а наружу для банка —
   отдельный плоский экспорт/view в этой самой форме (с `id объекта` на
   каждой строке). Это же соображение может закрыть и вопрос 1: если банк
   ожидает именно такую плоскую форму на входе у себя, развязка
   «канонично внутри → плоско наружу» подходит под оба случая сразу.
