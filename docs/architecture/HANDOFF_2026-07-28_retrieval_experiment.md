## 3. Текущая задача: A/B эксперимент по ретриву

### Развилка, которую надо закрыть числами, а не спором

| | что это | цена |
|---|---|---|
| **A. Чанк-уровень** | нарезать корпус на чанки, эмбеддить чанки, ретривить чанки | ~40k доков × ~4 = ~160k эмбеддингов ≈ порядка $1 + новая таблица + второй HNSW |
| **B. Двухступенчато** | regex-префильтр ∪ ретрив по **готовым** док-эмбеддингам (HNSW уже построен) → чанкать только выживших → реранк | почти бесплатно, переиспользует всё из Агента 1 |

**Аналитический вывод сессии: A качественнее.** Причина — размывание
док-эмбеддинга: в статье на 2000 слов про экономику абзац про «ключевую
ставку» тонет в общем векторе. И **потеря recall на первой ступени
необратима** — недостанутый документ никогда не будет нарезан, ни GLiNER,
ни критик его не вернут. Потеря precision восстановима, recall — нет.

**Но разрыв уже́, чем кажется:** в B рядом с док-вектором работает regex по
`Ключевые слова` объекта, а regex ловит ровно случай «узкое упоминание в
широкой статье». Реальный recall B = `regex ∪ док-вектор`. Остаточный
разрыв — неявные/перефразированные упоминания («Яндекс выкатил модель» для
объекта «Действия конкурентов», когда Яндекса нет в ключевых словах).

### Вторая ось, вероятно более важная: представление запроса

«Запрос» — это объект наблюдения, короткая фраза («Ключевая ставка ЦБ»).
Косинус трёх слов против новостной статьи слаб при **любой** гранулярности
индекса. Что эмбеддить в `observation_object.embedding` — открытый вопрос
(в черновике схемы помечен `[открыто]`), и он влияет на recall сильнее,
чем док-vs-чанк.

### Сетка эксперимента (один harness, обе оси)

| | запрос = имя | имя+алиасы+ключевые | описание-абзац |
|---|---|---|---|
| regex только | — | recall | — |
| regex ∪ док-вектор (B) | recall | recall | recall |
| чанк-вектор (A) | recall | recall | recall |

A можно оценить **на сэмпле**, не делая полный бэкфилл: нарезать и
заэмбеддить только известно-релевантные документы + несколько тысяч
случайных.

### Метрики

```
recall@K (док-уровень):  сколько из 72 упоминаний ретривер поднял в топ-K
hit-rate (чанк-уровень): содержит ли поднятый чанк «Контекст (цитата)»
```

## 4. ⚠️ Блокеры, которые надо проверить ПЕРВЫМИ

Обнаружены при подготовке хэндоффа, до эксперимента не проверены.
**Оба могут обнулить план эвала.**

### 4.1 Даты не совпадают (высокий риск)

Упоминания в примере датированы **2026-06-09 … 2026-06-13** (июнь).
Наш корпус: мигрированный из `agent_1` (старый) + разовый прогон ingestion
27686 строк примерно от 2026-07-24 (июль, `start_at` = вчера).

**Если июньского окна в `clean_posts` нет — answer key банка неприменим
как есть**, и эвал придётся строить своим разметочным проходом по нашему
корпусу. Проверять это надо до всего остального.

```sql
SELECT min(time_post), max(time_post), count(*) FROM agent_1_v5.clean_posts;
SELECT date_trunc('day', time_post) d, count(*)
FROM agent_1_v5.clean_posts
WHERE time_post BETWEEN '2026-06-08' AND '2026-06-15'
GROUP BY 1 ORDER BY 1;
```

### 4.2 URL в упоминаниях — агрегаторные, не статейные (высокий риск)

Большая часть ссылок вида `dzen.ru/news/story/04970f0f...` — это
**story-страницы агрегатора Дзена**, а не URL конкретной статьи. Точное
сравнение по URL с нашим корпусом, скорее всего, **не сматчится вообще**.

Другие источники в упоминаниях выглядят статейными и матчибельными:
`3dnews.ru/1143489/...`, `1prime.ru/20260613/...`, `ria.ru/20260613/...`,
`news.ru/usa/genprokurory...`, плюс упоминаются spbit, habr, cnews, gazeta.

**Вывод:** матчинг, вероятно, придётся делать нечётким — по
`источник + дата + сходство заголовка/цитаты`, а не по URL. Это меняет
объём работы на шаге 0, заложить.

```sql
-- сколько вообще таких источников есть в корпусе
SELECT name_source, count(*) FROM agent_1_v5.clean_posts c
JOIN agent_1_v5.source s USING (id_source)
WHERE name_source ~* 'dzen|3dnews|1prime|ria|news\.ru|habr|cnews|gazeta|spbit'
GROUP BY 1 ORDER BY 2 DESC;
```

  усечка до 1024 + L2-ренормализация (`agents/agent_1/src/agent_1/embed_v5.py`).
- Тесты: `agents/agent_1/pytest.ini`, 85 тестов, `pythonpath = src`.
- Запреты из `AGENTS.md`: не трогать `agent_1.processing_jobs`, не запускать
